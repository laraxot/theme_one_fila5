# 4.5: Transparent scoring: staff see scores + criteria mapping

**Story ID:** 4.5
**Epic:** 4 — Audit & Compliance
**Slug:** transparent-scoring-view
**Status:** backlog

## Story

As a staff member,
I want to see my own evaluation scores mapped against the published criteria,
so that I understand exactly why I received the score I did, per PA transparency law.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. The staff portal exposes a read-only "My scores" view showing the authenticated staff member's own Scheda evaluation scores, each mapped to the specific criteria (name, weight/band) from 4.4's published grid that produced it. [Source: prd.md#NFR-REG-001 — "Transparent scoring: staff see evaluation scores + criteria mapping"]
2. The view is plain Blade, consistent with 3.6's and 4.4's staff-portal pattern (no Filament, no edit affordances). [Source: architecture.md#adr-002] [Source: laravel/Themes/One/docs/stories/3.6.staff-portal-readonly-view.story.md]
3. The view is reachable only by an authenticated staff member and shows only their own scores, tenant-scoped, reusing 3.6's auth/tenant-scoping pattern. [Source: prd.md#NFR-SEC-002] [Source: laravel/Themes/One/docs/stories/3.6.staff-portal-readonly-view.story.md]
4. The criteria referenced in the score mapping are the same records shown in 4.4's evaluation-criteria view — no separate or divergent criteria snapshot is introduced for scoring display. [Source: prd.md#NFR-REG-001] [Inference — data-consistency constraint linking 4.4 and 4.5]
5. If the staff member has no scored Scheda yet, the view renders a clear "no scores yet" state rather than an error or an empty table. [Inference — UX completeness requirement, mirroring 4.4's AC #4 pattern for consistency]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature tests (Pest) against the new route, reusing 3.6's staff-auth test fixtures/pattern and 4.4's criteria fixtures.
- **Fixtures:** `User` factory (staff role, tenant-scoped); scored `Scheda` records for that user; `CriteriValutazione` rows matching 4.4's fixture set so the mapping can be asserted end to end; a second staff user's scored Scheda, to test ownership exclusion.
- **Scenarios to prove each AC:**
  - AC #1: authenticated staff user sees their own Scheda scores, each row showing the mapped criteria name/weight.
  - AC #2: assert the response is a Blade view with no edit/save form controls.
  - AC #3: an unauthenticated request is redirected to login; staff user A cannot see staff user B's scores (ownership assertion, stricter than 4.4's tenant-only assertion).
  - AC #4: assert the criteria IDs/names referenced in this view's mapping are identical to those returned by 4.4's criteria view for the same tenant (cross-story fixture consistency check).
  - AC #5: a staff user with zero scored Scheda renders the "no scores yet" message, not a 500 or an empty table shell.
- **Edge cases:** a Scheda scored against a criteria row that has since been removed/changed in `CriteriValutazione` (historical mapping integrity — document and test the chosen behavior: show a "criteria no longer active" label rather than silently dropping the row, consistent with the audit-trail spirit of this epic); a staff member with scores across multiple evaluation cycles/years (all should display, not just the most recent).
