# 3.6: Staff portal: read-only Scheda view

**Story ID:** 3.6
**Epic:** 3 — Access Control & Security
**Slug:** staff-portal-readonly-view
**Status:** backlog

## Story

As a staff member,
I want a simple, non-Filament web page where I can view my own Scheda evaluation summary and progression history,
so that I can check my evaluation status without needing an admin-grade interface or additional training.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `Themes/One/app/Http/Controllers/StaffPortalController.php` exposes a route (e.g. `GET /staff-portal`) rendering `Themes/One/resources/views/staff-portal/index.blade.php` — a plain Laravel Blade view, not a Filament panel. [Source: architecture.md#adr-002 — "Build a lightweight Laravel Blade staff portal for read-only self-service views"; Source: prd.md#FR-007 — "Portal: simple Laravel Blade view (no Filament)"]
2. The page displays the logged-in staff member's own Scheda summary (evaluation type, year, status, scores) and progression history, sourced only from records the `staff` role's policy (3.2) permits. [Source: prd.md#FR-007 — "Display: own Scheda summary..., progression history"]
3. The page is strictly read-only: no edit, create, or delete controls are rendered, and the controller performs no write actions. [Source: prd.md#FR-007 — "No edit: read-only."]
4. Access to the route requires an authenticated session with the `staff` role (or any role, scoped to "own" data only, per 3.2's policy) — unauthenticated requests redirect to login. [Source: prd.md#FR-007 — "Access: login via PA SSO or email code."]
5. The controller and view enforce tenant scope via the `BelongsToTenant` trait/global scope delivered in 3.5 — no query on this page can return another tenant's data. [Source: prd.md#FR-005 — "Multi-tenant: ...tenant_id filter on all queries"]

## Tasks / Subtasks

- [ ] Create `Themes/One/app/Http/Controllers/StaffPortalController.php` with an `index()` action that loads the authenticated user's own Scheda and Progressioni records via policy-gated queries (AC: #1, #2, #5)
- [ ] Create `Themes/One/resources/views/staff-portal/index.blade.php` rendering Scheda summary and progression history, with zero edit/delete/create UI elements (AC: #2, #3)
- [ ] Register the staff portal route behind the standard `auth` middleware (session-based, per ADR-004) (AC: #4)
- [ ] Confirm every query in the controller passes through `SchedaPolicy::view()`/`viewAny()` from 3.2 rather than an unscoped query (AC: #2, #5)
- [ ] Write a feature test asserting a staff user sees only their own data and an unauthenticated request is redirected (AC: #2, #3, #4)

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature tests (Pest) hitting the route via `get()`/`actingAs()`; no e2e/browser test required for this story (visual QA can be manual).
- **Fixtures:** `User` factory with `staff` role and linked employee identity; `Scheda`/`ProgressioniApproval` factories (Epic 1 scope — use factories if available, otherwise minimal stubs) owned by that employee, plus records owned by a different employee to prove exclusion.
- **Scenarios to prove each AC:**
  - AC #1: route resolves and renders the Blade view (not a Filament panel route).
  - AC #2: response contains the staff user's own Scheda/progression data.
  - AC #3: response HTML contains no form/edit/delete controls (assert absence of relevant markup or route names).
  - AC #4: unauthenticated request redirects to login; authenticated `staff` request succeeds.
  - AC #5: response never contains a different tenant's data even if IDs are guessed/enumerated in the URL.
- **Edge cases:** staff user with zero Scheda records (empty state, not an error); staff user attempting to access another employee's Scheda via a manipulated query parameter (must be blocked by the 3.2 policy, verified here at the HTTP layer).
