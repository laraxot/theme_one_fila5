# 4.4: Evaluation criteria publish (staff portal visibility)

**Story ID:** 4.4
**Epic:** 4 — Audit & Compliance
**Slug:** evaluation-criteria-publish
**Status:** backlog

## Story

As a staff member,
I want to see the evaluation grid and scoring criteria in my staff portal,
so that I understand how my performance will be assessed before and after evaluation, per PA transparency law.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. The staff portal exposes a read-only "Evaluation criteria" view listing the current evaluation grid — criteria names, weights/scoring bands, and descriptions — for the authenticated staff member's tenant. [Source: prd.md#NFR-REG-001 — "Evaluation criteria public: publish evaluation grid in staff portal"]
2. The view is plain Blade, consistent with the existing staff portal pattern established in 3.6 (no Filament, no edit affordances). [Source: architecture.md#adr-002 — Filament admin + thin Blade staff portal] [Source: laravel/Themes/One/docs/stories/3.6.staff-portal-readonly-view.story.md]
3. The view is reachable only by an authenticated staff member and scoped to their own tenant's criteria set, reusing 3.6's auth/tenant-scoping pattern. [Source: prd.md#NFR-SEC-002] [Source: laravel/Themes/One/docs/stories/3.6.staff-portal-readonly-view.story.md]
4. If a tenant has not yet configured an evaluation grid, the view renders a clear "not yet published" state rather than an error or an empty table. [Inference — UX completeness requirement synthesized from the general staff-portal read-only pattern; not separately specified in prd.md]
5. The evaluation grid content displayed matches the same criteria set used to compute scores, so what staff see here is provably the same data 4.5's transparent-scoring view maps scores against. [Source: prd.md#NFR-REG-001] [Inference — consistency constraint linking 4.4 and 4.5's data source]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature tests (Pest) against the new route, reusing 3.6's staff-auth test fixtures/pattern.
- **Fixtures:** `User` factory (staff role, tenant-scoped, per 3.6's convention); `CriteriValutazione` factory/seeded rows for one tenant; a second tenant with no criteria configured, to test the empty state.
- **Scenarios to prove each AC:**
  - AC #1: authenticated staff user sees all criteria rows (name, weight/band, description) for their tenant.
  - AC #2: assert the response is a Blade view (not a Filament page/route) and contains no edit/save form controls.
  - AC #3: an unauthenticated request is redirected to login; a staff user from tenant A cannot see tenant B's criteria (cross-tenant assertion, mirroring 3.6's tenant-scope test).
  - AC #4: a tenant with zero `CriteriValutazione` rows renders the "not yet published" message, not a 500 or an empty table shell.
  - AC #5: assert the criteria list rendered here matches (by ID/name) the criteria set 4.5's scoring view references, using a shared fixture set between the two stories' tests where practical.
- **Edge cases:** a criteria set mid-update (some rows saved, some not) — this story should render whatever the current committed state is, no partial-save handling needed since this is read-only; very large criteria lists (pagination not required by any cited source, but note the assumption in the implementation if the list is rendered unpaginated).
